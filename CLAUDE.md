# CLAUDE.md — Flutter Personal Finance App

## Общие правила работы

1. **Обсуждение перед кодом**
   Прежде чем трогать код, обсуди только самые важные верхнеуровневые решения:

   * Логика поведения программы (смысл кнопок, расположение элементов и т.д.)
   * Что будет делать программа и что мы хотим, чтобы она делала

   Все низкоуровневые решения (названия классов, методов, переменных, отступы, выбор функций, способы реализации) оставляй на своё усмотрение, придерживаясь общепринятых стандартов Dart/Flutter, принципов чистой архитектуры и других правил проектирования (например: SOLID, separation of concerns, single responsibility).
   Обсуждать нужно только детали, которые реально влияют на поведение приложения. Все остальное реализуй сам, не отвлекая пользователя.

2. **Работа с кодом**

   * Реализуй **только одну фичу за раз**.
   * Перед изменением кода всегда спрашивай: “Я начинаю эту фичу. Можем ли мы уточнить все детали?”
   * Если нужны новые файлы, создавай их сам; если нужны существующие — решай сам, какие файлы задействовать. Пользователь не будет указывать файлы.
   * Не трогай сгенерированные файлы, файлы темы и onboarding без явного разрешения.

3. **Форматирование и анализ**

   * После любых изменений в коде обязательно выполнять:

     ```bash
     dart format . && dart fix --apply && flutter analyze
     ```
   * Повторять до тех пор, пока команда **не выдаст 0 ошибок, 0 предупреждений и 0 фиксов**.

4. **Git commit**

   * После успешного завершения всех исправлений и очистки ошибок/предупреждений/фиксов:

     * Напиши текст коммита **на английском**, **одной строкой**, без кавычек после типа изменения.
     * Следуй правилам **Conventional Commits**
       Пример: `feat: add monthly budget screen with validation`

## Модель и использование

* Использовать **Claude Sonnet** для большинства изменений.
* Использовать **Claude Opus** только для: сложной архитектуры, больших рефакторов, сложных багов.
* Для мелких исправлений или boilerplate можно использовать **Haiku**.

## Workflow фичи

1. Прежде чем писать код, обсудить фичу с пользователем: детали, ограничения, acceptance criteria.
2. Подтвердить план реализации.
3. Реализовать фичу.
4. Запустить:

   ```bash
   dart format . && dart fix --apply && flutter analyze
   ```

   До нулевого количества ошибок/предупреждений/фиксов.
5. Если что-то не так — исправить только выявленные проблемы, не трогая другие участки кода.
6. После успешной очистки — написать текст коммита в одну строку с Conventional Commits.
7. Очистить сессию (`/clear`) перед началом следующей фичи.

## Дополнительно

* Всегда уточняй, если что-то непонятно или есть неоднозначность в логике фичи.
* Любые предположения о поведении приложения должны быть согласованы.
* Каждый коммит должен быть **самодостаточным и тестируемым**.
